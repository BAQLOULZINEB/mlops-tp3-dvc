Le but : versionner les DONNEES comme le code

Au TP2 il manquait un maillon : les donnees. Si transactions.csv change, impossible de retrouver la version qui a entraine le modele. DVC fait pour les donnees et les modeles ce que Git fait pour le code.

L'image a retenir : le vestiaireGit garde le ticket (petit fichier .dvc avec l'empreinte md5), DVC garde le manteau (le gros fichier) dans son cache et son stockage.

Le code, fichier par fichier

Ouvre le projet dans VS Code : chaque script commence par le meme resume (ROLE / ENTREE / SORTIE / A RETENIR). Lis-les dans cet ordre, c'est l'ordre d'execution.

dvc.yaml                    -> la description du pipeline (remplace pipeline.py du TP2)
dvc.lock                    -> la photo des empreintes apres dvc repro (genere, ne pas editer)
data/transactions.csv.dvc   -> le ticket : md5 + taille du CSV
.dvc/config                 -> ou est le stockage distant (../dvc-stockage)

1. donnees.py

Role : Fabrique le jeu de 5000 transactions bancaires (synthetiques) avec une graine fixe.

Entree : rien (tirage aleatoire avec la graine 7)

Sortie : data/transactions.csv (5000 lignes, 568 fraudes)

A retenir : Meme graine = memes donnees pour toute la promo : c'est la base de la reproductibilite.

2. src/preparer.py

Role : Etape 1 du pipeline : decoupe les donnees en apprentissage (75 %) et test (25 %).

Entree : data/transactions.csv + params.yaml (section preparation)

Sortie : data/prepare/train.csv et data/prepare/test.csv

A retenir : Dans le TP3, c'est dvc.yaml qui lance ce script (dvc repro), seulement si ses dependances changent.

3. src/entrainer.py

Role : Etape 2 du pipeline : entraine une foret aleatoire sur train.csv.

Entree : data/prepare/train.csv + params.yaml (section entrainement)

Sortie : models/model.pkl

A retenir : Relance par dvc repro uniquement si train.csv, ce script ou un parametre entrainement.* change.

4. src/evaluer.py

Role : Etape 3 du pipeline : mesure le modele sur le jeu de test.

Entree : data/prepare/test.csv + models/model.pkl

Sortie : reports/metrics.json (f1, precision, recall) + reports/confusion.png

A retenir : metrics.json est declare 'cache: false' : il reste dans Git pour etre compare (dvc metrics diff).

5. src/journaliser.py

Role : Cree un run MLflow qui pointe vers la version EXACTE des donnees (md5 lu dans le ticket .dvc).

Entree : params.yaml, data/transactions.csv.dvc, reports/metrics.json, dvc.lock

Sortie : un run 'donnees-xxxxxxxx' dans l'experience tp3-dvc

A retenir : Lien complet : tag commit (code) + tag donnees_md5 (donnees) + dvc.lock (tout le pipeline).

6. nouvelles_donnees.py

Role : Simule le mois suivant : ajoute 2000 transactions (plus de paiements de nuit) au CSV existant.

Entree : data/transactions.csv (v1, 5000 lignes)

Sortie : data/transactions.csv (v2, 7000 lignes, 936 fraudes)

A retenir : Apres ce script : dvc add met a jour le ticket avec une NOUVELLE empreinte md5.

Ce qu'il faut retenir

  • Meme donnee = meme md5 ; un octet change = empreinte totalement differente. C'est la preuve exacte de la version.
  • Deux push, deux destinations : git push (code + tickets -> GitHub) ET dvc push (donnees -> stockage). Oublier l'un = projet non reproductible.
  • dvc.yaml decrit, dvc repro decide : seules les etapes dont une dependance a change sont relancees ; dvc.lock est la photo des empreintes.
  • Plus de data/ ni models/ dans .gitignore : DVC ecrit ses propres .gitignore. Ne jamais faire git add ..
  • Metriques en cache:false : petit JSON lisible dans Git, comparable avec dvc metrics diff.
  • Git + DVC + MLflow : commit = quel code, md5 = quelles donnees, run = quels parametres et resultats.
Lecture critique : F1 0.8636 -> 0.8423Le modele v2 n'est pas forcement moins bon : le jeu de test a change (1750 lignes dont une population differente, plus de nuits). On ne compare des scores que sur le MEME jeu de test.

Pieges

'output is already tracked by SCM'Un fichier produit par le pipeline a ete ajoute a Git (git add .). Solution : git rm --cached puis dvc repro.
Stockage local../dvc-stockage est sur ta machine : un camarade qui clone verra les tickets mais ne pourra pas faire dvc pull. Il faut un remote partage (S3, GDrive...).

Commandes a connaitre

dvc init ; dvc add data/transactions.csv ; git add data/*.dvc data/.gitignore
dvc remote add -d stockage ../dvc-stockage ; dvc push ; dvc pull ; dvc status
dvc repro ; dvc dag ; dvc params diff ; dvc metrics diff ; dvc metrics show
git tag v1 ; git checkout v1 ; dvc checkout ; git checkout main ; dvc checkout
